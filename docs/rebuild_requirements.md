# Tunnelas 再構築 要件定義書

## 1. 文書情報

- 文書名: Tunnelas 再構築 要件定義書
- バージョン: v0.1
- 作成日: 2026-03-08
- 対象: 既存 TunnelDock を置き換える新アプリ `Tunnelas (tunnelas)` の新規プロジェクト

## 2. 背景

- 現行 TunnelDock は macOS メニューバーアプリとして価値を提供できている一方、今後の拡張と保守を見据えると、プロジェクト構成と責務分離を再設計したい。
- 新規プロジェクトでは、現行機能を参照しつつ実装をそのまま移植するのではなく、要件を整理し直した上で再構築する。
- 新アプリ名は `Tunnelas`、内部識別子・CLI/ディレクトリ表記は `tunnelas` を基準とする。
- 開発体験と保守性を安定させるため、ビルド基盤は Swift Package 中心から見直し、Xcode に最適化した構成へ移行する。

## 3. 目的

- macOS 上で SSH トンネルと `kubectl port-forward` を一元管理できるメニューバーアプリ `Tunnelas` を再構築する。
- 設定、状態管理、プロセス制御、UI を責務分離し、テストしやすい構造にする。
- 将来の機能追加に耐えられるプロジェクト構成と開発フローを定義する。

## 4. 再構築方針

- 新しいアプリは「既存コードの部分改修」ではなく「要件を再定義した上での新規実装」とする。
- ただし、ユーザー価値の中核である以下は初期リリースで維持する。
  - SSH トンネル管理
  - Kubernetes ポートフォワーディング管理
  - メニューバーからの起動・停止
  - 実行状態とエラーの可視化
- 設定ファイルの互換性は可能な限り維持し、利用者の移行コストを抑える。

## 5. 対象ユーザー

- 日常的に SSH トンネルを使う開発者
- Kubernetes 環境で `kubectl port-forward` を使って検証する開発者
- GUI より設定ファイル管理と再現性を重視する個人開発者・少人数チーム

## 6. スコープ

### 6.1 In Scope

- macOS ネイティブのメニューバーアプリ
- SSH トンネルの定義・起動・停止
- Kubernetes ポートフォワードの定義・起動・停止
- 設定ファイル読み込み、検証、再読み込み
- ルール単位およびグループ単位の状態表示
- エラー表示とログ参照
- スリープ復帰時の再接続
- アプリ終了時の管理プロセス停止
- XcodeGen を利用した Xcode プロジェクト生成

### 6.2 Out of Scope

- Windows / Linux 対応
- GUI による設定編集
- 設定のクラウド同期
- 秘密情報の保管機能
- 初期リリース時点での大規模プラグイン機構

## 7. 機能要件

### 7.1 設定管理

- FR-001: アプリ起動時に `~/.config/tunnelas/config.json` を読み込めること。
- FR-002: 設定ファイルの構文・必須項目・値域を検証できること。
- FR-003: 設定不正時はアプリが異常終了せず、利用者に原因を表示できること。
- FR-004: 利用者が手動で設定再読み込みを実行できること。
- FR-005: 再読み込み失敗時は直前の有効な設定を保持できること。

### 7.2 SSH トンネル

- FR-101: SSH ホストごとに複数の forward ルールを定義できること。
- FR-102: ホスト単位で配下ルールを一括起動・停止できること。
- FR-103: ルール単位で起動・停止できること。
- FR-104: 各ルールの状態を `stopped` / `starting` / `running` / `error` として表示できること。
- FR-105: 一部ルールの失敗が他ルールの起動継続を妨げないこと。

### 7.3 Kubernetes ポートフォワーディング

- FR-201: Kubernetes コンテキストごとに複数の forward ルールを定義できること。
- FR-202: コンテキスト単位で配下ルールを一括起動・停止できること。
- FR-203: ルール単位で起動・停止できること。
- FR-204: `target.kind` として少なくとも `svc` と `pod` を扱えること。
- FR-205: 各ルールの状態を SSH と同等の粒度で表示できること。

### 7.4 UI / 操作

- FR-301: アプリは macOS メニューバーに常駐できること。
- FR-302: グループ一覧と配下ルール一覧をメニュー内で確認できること。
- FR-303: グループ単位・ルール単位の起動/停止操作を提供すること。
- FR-304: 失敗時はエラー概要を UI 上で確認できること。
- FR-305: 直近ログを確認する導線を提供すること。

### 7.5 プロセス管理

- FR-401: 各ルールに対応する外部プロセスを個別に追跡できること。
- FR-402: 停止操作時に対象プロセスを安全に終了できること。
- FR-403: アプリ終了時に管理対象プロセスを残さないこと。
- FR-404: スリープ復帰時に、復帰前に起動中だったルールの再接続を試行できること。
- FR-405: 二重起動や停止競合で状態が破綻しないこと。

### 7.6 ログ / 観測性

- FR-501: 起動、停止、失敗、再接続のイベントを記録できること。
- FR-502: stdout / stderr をルール単位で追跡できること。
- FR-503: 代表的な失敗理由を利用者が判別できる表現で表示すること。

## 8. アーキテクチャ要件

- AR-001: UI 層、アプリケーション層、ドメイン層、外部コマンド実行層の責務を分離すること。
- AR-002: 状態遷移ロジックは UI から独立してテストできること。
- AR-003: `ssh` / `kubectl` / ファイル読み込み / ログ出力は差し替え可能な抽象を持つこと。
- AR-004: 新規実装では並行処理の競合を避けるため、状態管理の同期戦略を明示すること。
- AR-005: 将来の機能追加時に、コアロジックへ UI 依存を持ち込まないこと。

## 9. プロジェクト構成要件

- PRJ-001: 新しいプロジェクトは XcodeGen を用いた Xcode プロジェクト管理とすること。
- PRJ-002: `project.yml` をプロジェクト定義の唯一の編集対象とし、生成物の `.xcodeproj` を手編集しないこと。
- PRJ-003: `xcodegen generate` により、開発者が同一構成の Xcode プロジェクトを再生成できること。
- PRJ-004: アプリ本体、コアロジック、テストターゲットを分離したターゲット構成を持つこと。
- PRJ-005: CI またはローカル検証で XcodeGen 生成、ビルド、テストを一貫して実行できること。
- PRJ-006: 将来の macOS App Sandbox、署名、配布設定を追加しやすい構成にしておくこと。

## 10. 非機能要件

- NFR-001: サポート対象 OS は macOS 最新版から 2 世代前までを目安とする。
- NFR-002: 設定 100 ルール規模でも、通常操作で UI が著しく固まらないこと。
- NFR-003: 1 ルールの失敗がアプリ全体のクラッシュに直結しないこと。
- NFR-004: コアロジックは自動テストで継続検証できること。
- NFR-005: 障害時に調査可能なログを残せること。
- NFR-006: 外部コマンド未導入や設定不備を利用者が把握できること。

## 11. 開発ワークフロー要件

- WF-001: 実装タスクは GitHub Issues を単位として管理すること。
- WF-002: 要件定義、基盤構築、機能追加、移行対応などのフェーズごとにブランチを作成して作業すること。
- WF-003: 各ブランチの変更は GitHub 上でレビュー可能な形で Pull Request を作成すること。
- WF-004: Pull Request は GitHub 上でレビュー承認を得てからマージすること。
- WF-005: マージ前に、そのフェーズで必要なビルド・テスト・確認項目が完了していること。
- WF-006: Issue、ブランチ、Pull Request が相互に追跡できる状態を維持すること。

## 12. 現行 `config.json` 詳細仕様

### 12.1 現行ファイルパス

- 現行 TunnelDock は `~/.config/tunneldock/config.json` を既定パスとして読み込む。
- 新アプリ `Tunnelas` では `~/.config/tunnelas/config.json` を既定とするが、初期移行では現行仕様を互換対象として扱う。

### 12.2 現行トップレベル構造

```json
{
  "version": 1,
  "ssh": [],
  "kubernetes": []
}
```

- `version`: 必須の整数。現行実装では `1` のみサポート。
- `ssh`: SSH ホスト設定の配列。省略不可。
- `kubernetes`: Kubernetes コンテキスト設定の配列。省略不可。

### 12.3 現行 SSH 設定仕様

`ssh[]` の各要素は以下の構造を持つ。

```json
{
  "id": "bastion-dev",
  "enabled": true,
  "host": "bastion.dev.local",
  "user": "ec2-user",
  "port": 22,
  "forwards": [
    {
      "id": "db",
      "enabled": true,
      "localPort": 15432,
      "remoteHost": "127.0.0.1",
      "remotePort": 5432,
      "tags": ["database", "critical"]
    }
  ]
}
```

- `id`: 必須の文字列。`ssh[]` 配列内で一意。
- `enabled`: 任意の真偽値。省略時は `true` として扱う。
- `host`: 必須の文字列。SSH 接続先ホスト名。
- `user`: 必須の文字列。SSH 接続ユーザー。
- `port`: 必須の整数。1 から 65535。
- `forwards`: 必須の配列。ホスト配下のポートフォワード設定を表す。

`ssh[].forwards[]` の各要素は以下の構造を持つ。

- `id`: 必須の文字列。各 `forwards[]` 配列内で一意。
- `enabled`: 任意の真偽値。省略時は `true` として扱う。
- `localPort`: 必須の整数。1 から 65535。
- `remoteHost`: 必須の文字列。転送先ホスト。
- `remotePort`: 必須の整数。1 から 65535。
- `tags`: 任意の文字列配列。SSH forward にのみ存在する。

### 12.4 現行 Kubernetes 設定仕様

`kubernetes[]` の各要素は以下の構造を持つ。

```json
{
  "id": "dev-cluster",
  "enabled": true,
  "context": "dev",
  "forwards": [
    {
      "id": "api-svc",
      "enabled": true,
      "namespace": "default",
      "target": {
        "kind": "svc",
        "name": "api"
      },
      "localPort": 18080,
      "remotePort": 8080
    }
  ]
}
```

- `id`: 必須の文字列。`kubernetes[]` 配列内で一意。
- `enabled`: 任意の真偽値。省略時は `true` として扱う。
- `context`: 必須の文字列。`kubectl` で使うコンテキスト名。
- `forwards`: 必須の配列。コンテキスト配下のポートフォワード設定を表す。

`kubernetes[].forwards[]` の各要素は以下の構造を持つ。

- `id`: 必須の文字列。各 `forwards[]` 配列内で一意。
- `enabled`: 任意の真偽値。省略時は `true` として扱う。
- `namespace`: 必須の文字列。
- `target.kind`: 必須の文字列。現行実装では `svc` または `pod`。
- `target.name`: 必須の文字列。対象 Service または Pod の名前。
- `localPort`: 必須の整数。1 から 65535。
- `remotePort`: 必須の整数。1 から 65535。

### 12.5 現行バリデーション仕様

- `version` が `1` 以外の場合は不正とする。
- `ssh[].id` は `ssh[]` 配列内で重複不可。
- `kubernetes[].id` は `kubernetes[]` 配列内で重複不可。
- `ssh[].forwards[].id` は同一ホスト配下で重複不可。
- `kubernetes[].forwards[].id` は同一コンテキスト配下で重複不可。
- `ssh[].port`、`ssh[].forwards[].localPort`、`ssh[].forwards[].remotePort`、`kubernetes[].forwards[].localPort`、`kubernetes[].forwards[].remotePort` は 1 から 65535 の範囲内であること。
- `ssh[].forwards[].tags` は空文字を許可しない。
- `ssh[].forwards[].tags` は前後空白付き文字列を許可しない。
- `ssh[].forwards[].tags` は trim 後の重複を許可しない。
- `kubernetes[].forwards[].target.kind` は `svc` または `pod` のみ許可する。

### 12.6 新アプリでの取り扱い方針

- `Tunnelas` は初期段階で現行 `config.json` の構造を理解できることを最低条件とする。
- 既定パス変更に伴い、読み込みパスの移行戦略を明示する。
- 将来 `Tunnelas` 独自フィールドを追加する場合でも、互換レイヤーなしで既存利用者を破壊しない方針を採る。

## 13. 移行要件

- MR-001: 初期リリースでは既存 `~/.config/tunneldock/config.json` の主要構造との互換性を可能な限り維持し、新しい既定パス `~/.config/tunnelas/config.json` へ移行できること。
- MR-002: 利用者が既存設定を大きく書き換えずに新アプリへ移行できること。
- MR-003: 互換性を維持できない項目が出る場合は、移行手順または変換方針を文書化すること。

## 14. 受け入れ基準

- AC-001: `XcodeGen` から Xcode プロジェクトを生成し、アプリをビルドできる。
- AC-002: 正常な設定ファイルを読み込んでメニューバーにグループとルールが表示される。
- AC-003: SSH と Kubernetes の両ルールを UI から起動・停止できる。
- AC-004: ルール失敗時に状態が `error` となり、原因を確認できる。
- AC-005: 設定再読み込み失敗時も直前の有効設定と稼働中ルールが維持される。
- AC-006: スリープ復帰時に対象ルールの再接続が行われる。
- AC-007: 自動テストでコアロジックの主要状態遷移を検証できる。
- AC-008: 実装フェーズごとに GitHub Issue、対応ブランチ、Pull Request が紐づき、レビュー承認後にマージされる。
